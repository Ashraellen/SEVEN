## 3. Existing APM precedent recovered

Relevant prior architecture was recovered from:
`MemorySystem/SESSIONS/Transcripts/MAINMEMORYSYSTEM_016/TRANSCRIPT_0005.md`

That earlier book workflow established the pattern:

`Writer → Controller → Orchestrator`

Recovered role logic:

### Writer / Executor
- performs the prose-development/writing task;
- works from the current source/canon/task package;
- does not independently redefine canon or project architecture.

### Controller
- editorial opponent with corpus-level canon memory;
- not co-author, not muse, not second writer;
- checks whether declared canon is actually executed in prose;
- tracks repetition, seams, unconscious drift, character voices, motifs and metaphors across the corpus;
- acts as a cold-reader/editorial stress test;
- checks that architecture does not replace live scenes;
- checks that expansion adds novel substance rather than filler;
- preserves strong source passages where applicable;
- does not decide plot branches on behalf of the author;
- records its review and returns a concise completion/status message for routing.

### Orchestrator / Main project chat
- does not primarily write prose or replace Controller judgment;
- opens work units/tasks;
- routes assignments to Writer and Controller;
- tracks active chapter/unit, source, versions, reviews and revisions;
- maintains process state and author gates;
- receives short completion reports and issues the next short launch/task message;
- functions partly as routing/mail while also supervising both production roles.

The author explicitly described this earlier working model as convenient and suitable for working even while occupied elsewhere: executor completes the task, reports briefly; main/orchestrator chat gives a short Controller launch; Controller reviews/writes review to file and reports briefly; result returns to main/orchestrator chat for the next transition.
